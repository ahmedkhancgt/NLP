# Chapter 13: Expressiveness and Content Dilemmas

## Core Idea
Deciding what to include in a semantic model — how many lexicalizations, how granular distinctions should be, how general entities can be, how much negative knowledge and how many contextual "truths" to represent, and how interlinked to be with other models — is a series of cost/benefit dilemmas, not a maximize-everything exercise, because every addition carries ambiguity, maintenance, or disambiguation costs.

## Frameworks Introduced
- **Lexicalization Cost/Benefit Framework**: decide which candidate lexicalizations (synonyms, nicknames, acronyms, translations, shortened forms) to keep for a model element.
  - When to use: whenever adding a new natural-language label to an entity/relation.
  - How: if the model is just for browsing/reference, add freely (ambiguity is tolerable since humans disambiguate via context/descriptions). If the model feeds an automated tagging/detection system, measure the lexicalization's actual impact empirically: build two system versions (with/without the candidate term), run both on the same data, and compare the tagging differences for net correctness. For scale, use faster heuristic proxies: quantitative anomaly detection (sudden spike in detection rate after adding a term), cross-checking known ambiguity in external lexicons (WordNet, DBpedia), word-sense-induction methods, and six simple red-flag heuristics (shortened form, acronym, translation, multi-part-of-speech word, word count, cross-lingual mismatch).
- **Granularity Decision Procedure**: decide whether two closely related terms/meanings (e.g., violin/fiddle, Data Scientist/Data Analyst) should be modeled as the same or distinct elements.
  - When to use: whenever a near-synonym or subtle distinction is under consideration.
  - How: ask (1) is the meaning difference substantial/pragmatic or benign/theoretical? (2) what are the real consequences of making vs. not making the distinction? (3) can you actually support the distinction (data, modeling framework, downstream application capability)? Accept that granularity will end up uneven across the model — fine, as long as it's aligned with what users/applications can tolerate and is clearly documented.
- **Generality Decision Procedure**: decide whether to include very general/abstract entities (e.g., "Analysis," "Technology," "Engineering") in a model.
  - When to use: whenever a candidate entity sits at a high level of generality spanning many domains.
  - How: evaluate the entity's informational value (do people/users immediately think of something more specific when they encounter it bare? If so, it likely has low informational value and high natural-language ambiguity risk) and add general entities only "on demand," never pre-emptively by borrowing wholesale from an upper ontology or adding ever-broader root concepts without a concrete need.
- **Negative Knowledge Inclusion Criteria**: four conditions under which explicit negative assertions (e.g., "Karl Marx did not believe X") are worth adding.
  - When to use: deciding whether to represent that something is NOT the case, rather than relying on silence or positive-knowledge inference.
  - How: include a negative assertion when (1) it cannot be inferred or substituted via other elements (e.g., complementary crisp classes, or a functional relation's single stated value); (2) it is an important part of the element's actual meaning; (3) it refutes a common mistaken belief; or (4) it helps correct/retrain a downstream extraction system's errors.
- **Truth Contextualization Criteria**: parallel to Ch. 12's fuzzification gating questions, for deciding whether to represent multiple context-dependent "truths" rather than one.
  - When to use: when a statement's truth genuinely varies by context (e.g., "tall," "middle class," culturally-relative norms).
  - How: contextualize only when disagreement is high and hard to resolve by consensus, truth contexts can be identified cost-effectively, consuming applications can actually use contextualized elements, contextualization measurably reduces disagreement, and the benefits outweigh the context-management overhead. Start with the minimum viable granularity of contexts (continents before countries before cities) rather than building a full context taxonomy upfront — and remember contextualization and fuzzification are complementary, not either/or (disagreement can persist within a single context, calling for fuzzification; fuzzy degrees can themselves vary by context, calling for contextualization).
- **Interlinking Risk/Benefit Framework**: four-step evaluation before interlinking your model to an external one, replacing blind adherence to Linked Data "best practices."
  - When to use: whenever considering `owl:sameAs`/`skos:exactMatch`-style mapping to a third-party model.
  - How: (1) scrutinize the external model's quality/compatibility (reuse Ch. 7/8 scrutiny techniques — default to low a priori trust); (2) demand to understand the external model's management/evolution strategy (how often and how unpredictably does it change, and could those changes harm you?); (3) assess the actual cost/effort of interlinking and maintaining the interlink (often more about differing contexts of use than differing technology); (4) assess the concrete benefit (chiefly: is the external model a widely adopted standard whose omission would hurt your interoperability? if you just want the content, prefer selective merging over a standing interlink).

## Key Concepts
- **Two reasons for lexicalizations**: clarifying an element's meaning for humans (even a clear name benefits from common synonyms), and enabling automated detection of mentions in text — but every additional lexicalization raises the probability of introducing an ambiguous term, which can hurt downstream tagging precision.
- **Ambiguity red-flag heuristics for candidate lexicalizations**: shortened/abbreviated forms of multiword names (e.g., "Excel" vs. "Microsoft Excel" — shortening tends to broaden/alter meaning since dropped words were usually disambiguating); acronyms (notoriously ambiguous outside narrow domains); cross-language translations (a term unambiguous in the source language can become ambiguous in the target, e.g., Spanish "recuperación de datos" also meaning "data restoration"); words that can take multiple parts of speech (verb/noun/adjective ambiguity); and simply term length (shorter terms are statistically more likely to be ambiguous).
- **Controversial/discriminatory lexicalization risk**: politically/socially controversial terms (e.g., contested historical-event naming) and the flip side — omitting gender-neutral occupation terms can itself be seen as discriminatory. The chapter's practical recommendation: keep rejected lexicalizations in reserve (don't use them yet) rather than discarding them, since future improved disambiguation capability may make them usable later.
- **Granularity as subjective and context-dependent**: a semantic distinction that matters deeply to one audience (e.g., violin vs. fiddle for classical musicians) may be irrelevant to another, and the "right" granularity is a function of audience, downstream disambiguation difficulty, and downstream semantic-matching needs, not an objective fact about the terms.
- **Granularity hurts both disambiguation and semantic matching**: finer distinctions mean more possible meanings per term to disambiguate (harder, especially when distinctions are subtle or language-dependent, e.g., French "soudage" covering both "welding" and "soldering"), AND more cases where a downstream matching system (e.g., résumé-to-vacancy matching) needs an explicit relatedness relation to bridge genuinely-different-but-practically-interchangeable concepts.
- **Generality ≠ ambiguity**: a highly general entity (e.g., "Engineer") is not inherently ambiguous — WordNet still gives it one coherent, broad definition — but its low informational value in casual natural-language use (people assume a narrower specific meaning by default, e.g., assuming "technology" means software/electronics) creates practical disambiguation risk.
- **Empirical evidence of upper-ontology modeling difficulty**: a study (Stevens et al.) asking 8 BFO experts to classify 46 common travel-domain entities found only 51% mean agreement with an expert panel's classification and a Fleiss Kappa of just 0.52 — concrete evidence that highly general/abstract-entity classification is genuinely hard even for trained experts, reinforcing why no single upper ontology has become a widely accepted standard.
- **Negative knowledge's distinct informational value**: positive knowledge (or its absence) cannot substitute for negative knowledge — "not tall" isn't equivalent to "short" (vague classes aren't complementary, per Ch. 7), and knowing someone lived in Canada doesn't tell you they didn't also live elsewhere. But exhaustively representing all negative facts is impractical (and often framework-unsupported), so negative assertions should be added selectively per the four inclusion criteria, not wholesale or never.
- **Multiple truths / context-dependent statements**: the same statement (Stephen Curry is "tall," $25,000/year is "middle class") can be true in one context and false in another — representing all contexts explicitly is often impractical because contexts can be too numerous, hard to identify/define, or unusable by the consuming application (e.g., an app that just wants "the" skill set for a profession can't consume a context-indexed skill set without knowing which context to pick).
- **Context reasoning complexity**: once you build a nontrivial context taxonomy/ontology (e.g., geographic hierarchy), you need reasoning support to propagate truth correctly (a Europe-wide-true statement should be inferred true in each European country; a partially-true-across-countries statement needs an aggregation rule for the continent level) — the chapter poses this as an open modeling challenge without a ready formula.
- **Interlinking is not an unconditional good despite Linked Data's "Four Rules"**: Tim Berners-Lee's four Linked Data publishing rules (use URIs, use HTTP URIs, provide RDF info on lookup, link to other URIs) are framed by the chapter's author as best practices to weigh against real costs, not obligations — interlinking can actively reduce a model's value if the external model's quality, governance, or evolution pattern don't fit your needs.
- **Interlinking cost is mostly about differing context, not differing technology**: merging/mapping models is costly less because of incompatible formalisms and more because of differing development/usage contexts (goals, strategy, quality bar) that produce genuinely incompatible granularity, lexicalization optimization, and relation semantics even when the surface schema looks similar.

## Mental Models
- **Every addition to a model has a cost, not just a benefit**: lexicalizations, fine-grained distinctions, general root entities, negative assertions, context variants, and interlinks all introduce maintenance burden, ambiguity risk, or disambiguation difficulty — treat every "should we add X?" question as a cost/benefit analysis, not a default "more is better."
- **Granularity, generality, negation, context, and interlinking are all instances of the same underlying trade-off**: expressivity/content richness vs. manageable complexity/ambiguity — the same kind of gating questions (impact, cost, benefit, application capability) recur across all five dilemmas in this chapter.
- **Keep what you reject, don't discard it**: rejected lexicalizations (and implicitly, other deferred distinctions) should be retained in reserve for future reuse once tooling/application capability improves, rather than being permanently lost.
- **Default trust toward external models should be low, not high**: scrutinize before interlinking, since differing goals/strategy/quality standards between models (even in the same domain) are the norm, not the exception.

## Anti-patterns
- **Adding every possible lexicalization "just in case"**: increases ambiguity risk linearly with each addition, especially for downstream automated tagging systems that can't handle the added ambiguity.
- **Treating shortened forms, acronyms, translations, and multi-part-of-speech words as safe to add without scrutiny**: each of these categories has a statistically elevated chance of introducing ambiguity (per the six heuristics).
- **Ignoring controversial/discriminatory lexicalization implications**: either including politically contested terms carelessly, or omitting necessary inclusive terms (e.g., gender-neutral occupation names) and thereby appearing discriminatory by omission.
- **Chasing every theoretically-findable semantic distinction**: "if you look hard enough on the web for differences in the meanings of very close terms, you will almost always find some" — treating any discoverable distinction as model-worthy regardless of practical importance (the Software Engineer vs. Software Developer example, judged by the author as "benign, if not a bit artificial").
- **Modeling fine-grained distinctions nobody asked for and nobody can support**: adding a distinction (e.g., violin/fiddle) without the supporting information (playing-style difference), knowledge-acquisition sources, framework capability, or downstream application capability needed to make it meaningful or usable.
- **Pre-emptively importing upper-ontology generality into a domain-specific model**: adding `Engineering` atop a `CivilEngineering`-rooted taxonomy "just because," or building a domain model by specializing a full upper ontology from the top down, without a concrete need driving the addition.
- **Confusing generality with ambiguity (or vice versa)**: assuming a broad/general entity must be ambiguous (it may have one coherent broad definition) or assuming a narrow/specific entity can't be ambiguous.
- **Exhaustively representing all negative facts**: attempting to state everywhere someone wasn't born, didn't marry, etc. — impractical, often framework-unsupported, and usually unnecessary once positive/functional relations and complementary crisp classes already imply the negation.
- **Treating negative knowledge as unnecessary or an afterthought**: the opposite failure — never adding negative assertions even when they carry real, non-inferable information (refuting common misconceptions, documenting what a course does NOT cover, correcting a recognition system's known false positives).
- **Representing context-dependent truths as if they were universal**: stating "$25,000/year is middle class" as a flat, context-free fact when it is genuinely only true in some countries.
- **Building a full context taxonomy/ontology before validating the need**: jumping straight to city- or postal-code-level geographic contextualization (or a detailed org-chart-level business-function taxonomy) instead of starting with the minimum viable granularity (continents/countries, or core business functions).
- **Treating fuzzification and contextualization as mutually exclusive alternatives**: picking one and assuming it fully resolves vagueness/context-dependence, when disagreement can persist within a context (needing fuzzification) or fuzzy degrees can themselves vary by context (needing contextualization) — they are complementary tools.
- **Interlinking reflexively because of Linked Data "best practice" pressure**: adopting Berners-Lee's four rules as an obligation rather than weighing the actual risk/benefit for your specific model and context.
- **Accepting all of an interlinked external model's attached information wholesale**: as the Ch. 7 "bad mapping" pitfall warns, interlinking to ESCO (or any external model) does not mean automatically importing its lexicalizations, attributes, or relations without scrutiny — Textkernel's actual solution was to link entities but explicitly block automatic import of ESCO's additional information, selectively curating only what was useful/correct/compatible.
- **Assuming structurally similar models (same taxonomy shape, same relation types) are semantically compatible**: ESCO and Textkernel's knowledge graph looked superficially alike (profession/skill taxonomies, multilingual lexicalizations, essential/optional relations) but differed substantially in granularity (Data Scientist/Data Engineer merged in ESCO but split in Textkernel's graph; language skill granularity reversed) and in lexicalization/relation quality (ESCO's essential/optional relations were poorly documented and inaccurate against Textkernel's benchmark data).

## Reference Tables

(6) does it already appear as a lexicalization of another entity in your own or an external model (WordNet, DBpedia)?

## Worked Example
The Textkernel/ESCO interlinking case study directly applies the chapter's own framework: despite ESCO and Textkernel's knowledge graph looking structurally similar (profession/skill taxonomies with multilingual labels and essential/optional skill relations), close inspection revealed granularity mismatches (ESCO merged Data Scientist/Data Engineer and Finance/Economics, which Textkernel's graph split; conversely ESCO distinguished speaking/understanding/writing a language, which Textkernel's graph did not), lexicalization-quality mismatches (ESCO's labels weren't optimized for text-based entity detection/disambiguation the way Textkernel's were), and relation-quality mismatches (ESCO's essential/optional skill relations were poorly documented and inaccurate against Textkernel's own benchmark data). On the benefit side, ESCO was becoming a shared European public-employment-agency standard (strong interoperability value), offered useful lexicalizations in languages Textkernel's graph lacked, and changed on a predictable, slow (roughly annual) cadence. The resulting decision was a deliberate middle ground: link Textkernel's entities to ESCO's (capturing the standard-alignment benefit) while explicitly blocking automatic import of ESCO's attached lexicalizations/attributes/relations, instead manually curating only the subset judged useful, correct, and semantically compatible with Textkernel's own model.

## Key Takeaways
1. Treat every candidate lexicalization as a cost/benefit decision driven by the model's actual usage (browsing/reference tolerates ambiguity; automated tagging does not) — use empirical A/B tagging-difference testing when stakes are high, and heuristic red flags when scale demands speed.
2. Granularity decisions should weigh whether a distinction is substantial/pragmatic (not just theoretically discoverable), what the real consequences of (not) making it are, and whether you can actually support it — expect and accept uneven granularity across a model as long as it's documented and tolerable to consumers.
3. General/abstract entities are not inherently ambiguous, but often carry low informational value in natural-language use and are genuinely hard to classify consistently (even by trained ontologists) — add them only on demand, never pre-emptively.
4. Negative knowledge carries information positive knowledge cannot substitute for, but should be added selectively (non-inferable, meaning-defining, misconception-refuting, or extraction-correcting cases), not exhaustively.
5. Context-dependent "multiple truths" should only be explicitly modeled when disagreement is severe, contexts are identifiable cost-effectively, and consuming applications can actually use them — start with minimum-viable context granularity, and remember contextualization and fuzzification are complementary, not substitutes.
6. Interlinking to an external model is a risk/benefit decision, not an obligatory best practice — scrutinize the external model's quality, governance, and change pattern, and prefer selective content curation over wholesale automatic import even when you do interlink.
