# Chapter 14: Evolution and Governance Dilemmas

## Core Idea
Semantic models must evolve (fixing quality, expanding scope, retiring invalid elements) and that evolution must be governed (clear principles/processes/rules) — both require navigating genuine dilemmas (remember-or-forget, release pace, reactive-or-preventive, centralized-or-decentralized) rather than following a single correct template.

## Frameworks Introduced
- **Remember-or-Forget Decision Rule**: whether to fully delete removed/invalid statements or retain them in some recycled/negative/historical form.
  - When to use: whenever evolution requires removing a statement that was previously in the model.
  - How: keep (in some form) statements that have a high risk of reappearing (recycle as explicit negative knowledge to suppress recurring extraction errors, per Ch. 13) or that have standing historical value (e.g., a former capital city, a time-contextualized former headcount) for processing historical data; otherwise, let them go.
- **Run-or-Pace Evolution Cadence Framework**: deciding release frequency and release size.
  - When to use: designing a model's update/release schedule.
  - How: weigh four factors — the actual pace at which changes are needed, the pace at which you can implement them, the change value/overhead ratio (is each release worth its cost?), and the pace at which dependent applications/models can absorb changes. Define concrete release-worthiness criteria (e.g., "any accuracy fix in subdomain X ships immediately," "need ≥20% new statements to justify a release") and make the model "skip-safe" (compatible across skipped versions) so less change-tolerant dependents aren't allowed to throttle more change-tolerant ones.
- **React-or-Prevent Strategy**: balancing reactive (feedback-driven) vs. preventive (proactive-monitoring-driven) evolution.
  - When to use: structuring how a model detects the need for updates.
  - How: build feedback mechanisms that are comprehensive (cover all important model aspects), reliable (noise-free, trustworthy), and timely (actionable before it's too late); separate feedback about the model from feedback about the consuming application; ensure feedback is semantically compatible with the model (per Ch. 8's source-compatibility scrutiny); and make giving feedback easy/worthwhile. Complement with four-step proactive balancing: (1) assess each model part's susceptibility to decay, (2) assess each part's importance via risk/benefit (Ch. 9), (3) assess existing feedback-mechanism effectiveness for each part, (4) feed all learned issues back into both fixes and improved automated monitoring.
- **Semantic Drift Measurement Framework**: domain-adapted drift modeling and measurement, extending Ch. 3's generic label/intension/extension model.
  - When to use: prioritizing which parts of a model need more frequent maintenance attention.
  - How: (1) adapt the generic drift model to your domain — determine which of label/intension/extension actually matter for your entities (e.g., a labor-market graph's professions/skills are abstract with no meaningful extension, so drift is tracked via intension/lexicalization only) and weight sub-aspects by their actual contribution to meaning (e.g., `skos:broader` changes signal more fundamental drift than `skos:narrower`; essential skills matter more than optional ones for a profession's meaning); (2) choose similarity metrics appropriate to each aspect (set similarity for lexicalization/intension sets; rank-correlation metrics like Kendall's Tau for vague, fuzzy-degree-ranked relations, to detect re-ranking even when the same top-N related concepts persist); (3) build a parameterized, configurable measurement framework (target concept types, time scope, included relations, applicability context/provenance) since different parameter choices yield different drift values AND different interpretations (CV-sourced drift reflects workforce perspective; vacancy-sourced reflects industry perspective; news-sourced reflects general perception; encyclopedic-sourced reflects core meaning change) — aggregate via importance-weighted combination of per-relation/per-context drift scores.
- **Centralization-vs-Decentralization Governance Diagnostic**: ten factors to assess before choosing a model's governance structure.
  - When to use: designing or reforming a model's governance system.
  - How: lean centralized when development automation is low, modularity is low (parts' quality is interdependent), quality-monitoring automation is low, domain breadth/vagueness is low enough for a small expert group to cover, accuracy/conciseness matter more than completeness, downstream change impact is high, contributors lack shared goals/practices, the model is highly complex/specialized, conflict-resolution mechanisms are weak, or the organization's existing culture favors centralization — lean decentralized on the inverse of each factor. Different governance degrees can (and often should) be applied to different parts/tasks of the same model rather than picking one uniform policy.

## Key Concepts
- **When evolution can safely be ignored (rare)**: only if the model's first version already meets all required quality dimensions AND no external forces (domain change, scope expansion, rising quality bar) threaten that quality — in practice nearly every real model needs an evolution strategy.
- **Negative knowledge as error suppression**: recycling a removed erroneous statement as an explicit negative assertion prevents its recurring reintroduction by an automatic acquisition pipeline whose root-cause bug hasn't yet been fixed (direct callback to Ch. 13's negative-knowledge criteria).
- **Time-contextualized historical knowledge**: former-true statements (former capital city, past headcount) retain value when the model must process historical documents/data that referenced the old state.
- **Evolution pace trade-off (frequent-small vs. infrequent-large releases)**: no universal answer — real producers differ hugely (EMSI's Skill Taxonomy: biweekly; FIBO: quarterly) — driven by actual change need, implementation capacity, change value/overhead ratio, and dependent-system absorption capacity.
- **"Skip-safe" model versioning**: designing releases so an application can skip intermediate versions without being unable to adopt future ones — lets a model serve both highly responsive and highly change-averse dependents simultaneously (Textkernel's biweekly-vs-quarterly client split).
- **Unknown/public dependents**: a public model (DBpedia, SNOMED) may have many unknown downstream dependents you can't individually accommodate — the responsible move is a transparent, well-documented, predictable evolution strategy shared openly, not an obligation to satisfy every unseen consumer; this applies to commercial models too since "no model user likes unpredictability."
- **Reactive feedback mechanism quality criteria**: comprehensive (no blind spots on important model aspects), reliable (noise-free/trustworthy), timely (actionable before damage is done) — and critically, must isolate model-quality feedback from application-quality feedback (e.g., a film-search thumbs-down might reflect a bad ranking algorithm, not a bad semantic model) and must minimize friction for the feedback-giver (the Amazon recommendation-engine anecdote: a UX change from inline, contextual feedback buttons to an out-of-context "Improve my recommendations" page caused the author to simply stop giving feedback).
- **Preventive/proactive quality monitoring signals**: falling average per-document entity-detection count (possible completeness drop); falling percentage of entities with lexicalizations in a target language (linguistic divergence); rising count of statistical outliers (possible accuracy drop); rising count of wrong third-party links into your model (possible understandability drop); falling download/usage counts (possible overall value drop) — each is a signal (per Ch. 9's metric-vs-signal distinction), not a direct quality measurement.
- **Semantic drift's domain-specific weighting**: not all meaning-contributing aspects drift equally — e.g., in the labor-market knowledge graph example, extension is deliberately excluded from drift modeling (abstract entities like professions/skills have no meaningful instance set whose size change signifies drift), while intension (skills/activities for professions; similar skills/activities for skill concepts; developed/verified skills for qualifications) is the primary driver, lexicalization matters only for genuine label changes (not mere spelling/morphosyntactic variants), and `skos:broader` changes outweigh `skos:narrower` changes in drift significance.
- **Drift measurement for vague/fuzzy relations**: ordinary set-similarity breaks down when relations carry fuzzy strength degrees — compare top-N ranked related-concept lists between two time-versions using a rank-correlation metric (e.g., Kendall's Tau) so that even stable membership with re-ordered strength (e.g., Data Scientist's top-10 related skills staying the same set but changing rank) registers as drift.
- **Semantic drift's audience duality**: drift measurement serves model developers (prioritizing maintenance) AND model users directly (e.g., communicating actual labor-market evolution to job seekers, employers, educators, policymakers) — a job holder's narrow, static perception of their own profession's content can cause real-world friction (failed job searches, failed hiring) when it diverges from the profession's actual drifted meaning.
- **Governance spectrum (centralized ↔ decentralized)**: centralized = small homogeneous team as sole editors/decision-makers; decentralized = collective, heterogeneous, multi-group editing/planning/decision-making with no central authority — neither is inherently superior; both camps have valid arguments (expertise scarcity and bias-avoidance for centralization vs. collaborative Wikipedia-scale growth, as in DBpedia's coverage, for decentralization) that apply differently depending on context.
- **Clean-slate vs. legacy-integration governance starting point**: building from scratch favors starting centralized and decentralizing gradually/controllably; integrating multiple pre-existing models each with its own governance system means you can't just ignore those existing systems — you must reconcile them.

## Mental Models
- **Evolution and governance are two separate but linked disciplines**: evolution defines what changes and when; governance defines who decides and how — a good evolution strategy without governance to execute it reliably (or vice versa) still fails.
- **Drift measurement is domain-adapted, not generic**: the textbook label/intension/extension drift model is a starting template, not a fixed formula — each domain/model requires determining which aspects actually carry meaning-relevant change and weighting them accordingly.
- **Governance degree is diagnostic, not ideological**: neither centralization nor decentralization is a default "best practice" — ten concrete situational factors (automation, modularity, monitoring automation, domain breadth/vagueness, quality priorities, downstream change impact, shared goals, complexity, conflict-resolution effectiveness, organizational culture) determine the right degree, and different governance degrees can coexist for different parts/tasks of the same model.
- **The least-tolerant dependent sets the ceiling, unless you design around it**: without skip-safe versioning, a single change-averse consumer can throttle the whole model's evolution pace for everyone else.

## Anti-patterns
- **Treating model evolution as optional or a one-time afterthought**: ignoring that quality decays and domains/scope/requirements change over time unless the rare "stable first version, no external forces" condition genuinely holds.
- **Deleting all removed statements unconditionally**: losing valuable historical-context information (former capitals, former headcounts) or losing the ability to suppress recurring error patterns via negative knowledge.
- **Promising release cadences the team can't sustain**: committing to frequent releases without the implementation capacity to actually deliver needed changes at that pace.
- **Letting the most change-averse dependent silently dictate the model's overall release frequency**: without skip-safe design, a single low-tolerance consumer (e.g., a client wanting quarterly-only updates) can block faster releases for everyone else.
- **Assuming you must satisfy every unknown downstream dependent of a public model**: an unrealistic and unnecessary burden — the real obligation is a transparent, documented, predictable evolution strategy, not universal accommodation.
- **Building reactive feedback mechanisms that conflate model quality with application quality**: e.g., accepting a thumbs-down on search results as direct evidence the semantic model is wrong, when the actual cause may be the application's ranking algorithm.
- **Making feedback hard, out-of-context, or slow to act on**: directly discourages users from ever providing it again (the Amazon recommendation-engine UX regression anecdote).
- **Relying purely on reactive feedback with no proactive monitoring, or vice versa**: pure reactive risks missing issues feedback mechanisms can't surface comprehensively/reliably/timely; pure preventive risks missing issues only direct user feedback reveals — both need the four-step balancing process.
- **Using a generic, one-size-fits-all semantic-drift formula**: applying the textbook label/intension/extension framework uniformly without adapting which aspects matter and how much for your specific domain (e.g., naively including extension for abstract entities whose "instance count" changes don't actually reflect meaning drift).
- **Measuring drift on vague/fuzzy relations with plain set-similarity**: misses re-ranking-only drift (same top-N set, different relative strength ordering) that a rank-correlation metric would catch.
- **Reporting a single "the drift is X" number without specifying measurement parameters**: since target concept types, time scope, included relations, context, and provenance all change both the magnitude and the interpretation of drift, an unparameterized drift report is uninterpretable or misleading (e.g., conflating workforce-perspective drift from CVs with industry-perspective drift from vacancies).
- **Defaulting to either pure centralization or pure decentralization without diagnosing your actual situation**: neither "only experts should edit this" nor "let everyone contribute freely" is universally correct — both the DBpedia quality-problems argument and the DBpedia Wikipedia-scale-coverage argument are valid in different contexts.
- **Ignoring existing governance systems when integrating multiple pre-existing models**: the Textkernel case shows how four previously-independent, informally-governed teams produced accuracy mistakes (inconsistent definitions of "skill" and "synonym" across teams), conciseness problems (duplicate elements added without checking for existing equivalents), and uncontrolled maintenance overhead (ad hoc client-specific customizations) — all consequences of skipping deliberate governance reconciliation.
- **Applying uniform governance strictness to all types of changes**: treating a minor attribute-value edit with the same deliberation/consensus/documentation burden as a schema-level change (new entity type or attribute) wastes effort on low-risk changes while potentially under-scrutinizing high-risk ones — the fix is differentiated process by change type and model part.

## Worked Example
The Textkernel "centralization story" is a direct worked example of governance reform: before integration, four independent teams plus the author's new team had uncoordinated edit rights over disconnected semantic models, with inconsistent interpretations of core terms (what counts as a "skill," what counts as synonymous skill terms) causing accuracy errors, duplicate-element additions harming conciseness, and unchecked ad hoc client customizations inflating maintenance overhead. The remediation, implemented gradually: (1) consolidated primary editing/accountability from five teams down to two, while still allowing other teams limited indirect contribution; (2) tiered governance process by change type — schema-level changes (new entity types/attributes) required more deliberation/consensus/documentation than simple attribute-value edits; (3) centrally harmonized and documented definitions of vague core terms (e.g., "skill"), including renaming elements per Ch. 6's naming guidance to reduce ambiguity/vagueness; (4) increased automated quality-control/alerting coverage, which let more contributors participate safely without fear of silently breaking the model; (5) imposed stricter criteria for when/whether to create client-specific model customizations, preventing uncontrolled maintenance-overhead growth. The author notes this reform was still in progress at time of writing but had already measurably improved governance smoothness and efficiency — illustrating that governance reform is itself an evolutionary, incremental process, not a one-time fix.

## Key Takeaways
1. Nearly every real-world semantic model needs an explicit evolution strategy, since the conditions under which evolution can be safely ignored (perfect initial quality, no external pressures) are rare.
2. Decide what to do with removed/invalid statements deliberately — recycle as negative knowledge if they risk recurring, or retain as historical knowledge if useful for processing older data; otherwise let them go.
3. Release cadence should be driven by actual need, implementation capacity, change value/overhead, and dependent-system absorption capacity — not by a generic "frequent is better" or "infrequent is safer" assumption; use skip-safe versioning to serve dependents with different tolerance levels simultaneously.
4. Balance reactive (feedback-driven) and proactive (monitoring-driven) evolution based on each model part's susceptibility to decay, importance, and existing feedback-mechanism effectiveness — neither alone is sufficient.
5. Semantic drift measurement must be adapted to your specific domain and model (which meaning-aspects actually matter, how to handle vague/fuzzy relations, which parameters to expose) rather than applying a generic formula — and the resulting drift values serve both internal maintenance prioritization and external communication to the model's actual users.
6. Governance centralization-vs-decentralization is a diagnostic decision based on ten concrete situational factors, not an ideological default — and different parts/tasks of the same model can warrant different governance degrees.
7. When integrating multiple previously-independent, informally-governed models, deliberately reconcile their governance (shared definitions, tiered change processes, consolidated accountability, automated quality controls, customization criteria) rather than assuming informal coexistence will work at scale.
