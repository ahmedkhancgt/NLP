# Chapter 7: Gradio and Hugging Face Deployment

## Core Idea
Deploying a Python project to the web requires understanding three roles — client (UI), server (logic), API (the contract between them) — and the Gradio library lets a Python-only developer generate a full web GUI and REST API in a handful of lines, which Hugging Face Spaces then hosts for free at scale.

## Frameworks Introduced
- **Client / API / Server deployment trio**: the three roles in every web/mobile app, mapped onto a Graphviz flow diagram (client -> API -> server, with a response arrow back).
  - When to use: before building any deployed application, to decide where logic should live.
  - How: client = GUI (Gradio generates its HTML/CSS/JS automatically); server = core logic/computation (where sensitive/complex logic belongs); API = the request/response contract connecting them (REST most common, using JSON).
  - Rule of thumb: client-side logic is fine for simple apps with no sensitive data (e.g. a calculator in pure JavaScript); anything needing data storage, auth, or heavy computation belongs server-side.
- **Gradio-first deployment**: write the Python function, wrap it in a Gradio `Interface`/components, call `.launch()` — Gradio auto-generates the front-end and a temporary public URL plus an auto-documented REST API ("Use via API" link) in multiple languages (Python/JavaScript/Bash).
  - When to use: turning any working Python function into an interactive, shareable web app without writing HTML/CSS/JS.
  - How: `import gradio as gr` -> define input/output components -> bind them to your existing function -> `demo.launch()`.
- **Hugging Face Spaces deployment pipeline**: the standard production path beyond Gradio's 72-hour temporary link.
  - When to use: deploying for persistent, shareable, scalable hosting.
  - How: (1) write `requirements.txt` (pinned library versions); (2) write `app.py` (pure application logic plus Gradio UI and `.launch()` only — keep credentials and test/debug code out of it); (3) create a Hugging Face Space (choose Gradio SDK, hardware tier); (4) add both files to the Space (via web UI or `git clone`/push); (5) Hugging Face auto-builds a container and deploys.

## Key Concepts
- **Client side**: the GUI/interactive layer (buttons, forms, images) a user directly touches; built with HTML/CSS/JS for web, Swift for iOS, Kotlin/Java for Android — or auto-generated by Gradio from Python.
- **Server side**: where core logic, computation, and data access run; centralizing logic here improves security (hides proprietary logic), consistency (same result regardless of client device), and scalability (dedicated CPU/GPU resources).
- **API (Application Programming Interface)**: the formal contract specifying what data a client sends and how a server responds; acts as the "middleman" so front-end and back-end can be built independently.
- **REST API**: uses standard HTTP methods (GET/POST/PUT/DELETE), typically returns JSON; the most common API style, simple but can require multiple calls for related data.
- **GraphQL**: an alternative (Facebook-developed) query style letting clients request exactly the data they need in one query, reducing over-/under-fetching.
- **requirements.txt**: a text file pinning exact library versions (e.g. `gradio==5.12.0`, `fastai>=2.7.18`) so a deployment environment installs compatible dependencies.
- **app.py**: the deployment convention for a self-contained application file holding only production logic (functions + Gradio interface + launch call) — no secrets, no test/debug code.
- **Container**: a lightweight, portable, self-sufficient bundle of code + runtime + dependencies ensuring consistent behavior across machines (commonly Docker/YAML-based); Hugging Face auto-generates this once you upload `requirements.txt` and `app.py`.
- **Inference engine / learner object**: the exported, pre-trained model object used at deployment time to make predictions — notably, deployment needs no training data or data loader, only the trained model.

## Mental Models
- Think of the API as a contract between two independently-working teams (front-end and back-end) — each side can change implementation freely as long as the contract (expected inputs/outputs) holds.
- Think of Gradio as "Wix/Squarespace for Python developers" — it automates front-end generation the same way drag-and-drop site builders do, but you stay in Python the whole time instead of learning HTML/CSS/JS.
- Treat local Jupyter testing as only step one: "a single user running a script on their laptop is very different from an application handling millions of users" — deployment to a scalable server is what distinguishes a personal project from a real application.
- Treat version pinning in `requirements.txt` as a time capsule: pin exact versions tested at development time so future dependency updates don't silently break your deployed app.

## Anti-patterns
- **Putting sensitive logic or data on the client side**: exposes proprietary algorithms/business rules in browser-visible source code; keep anything confidential or complex on the server.
- **Hardcoding credentials or secrets inside `app.py`**: use environment variables or separate config instead.
- **Mixing test/debug code into the production application file**: keep `app.py` limited to the functions, UI, and launch call that actually run in production.
- **Relying only on Gradio's temporary 72-hour share link for real deployment**: fine for quick demos/testing, but use Hugging Face Spaces (or another host) for persistent, scalable access.
- **Assuming a drag-and-drop website builder (Wix, Squarespace) can deploy an ML model**: these platforms cannot host/execute AI models in real time; CNN/ML deployment requires a code-based platform like Hugging Face with Fast.ai + Gradio.

## Code Examples
```python
import gradio as gr

# Calculator GUI (reusing the calculator() logic from Ch 3)
def calculator(num1, num2, operation):
    if operation == "add":
        return num1 + num2
    elif operation == "subtract":
        return num1 - num2
    elif operation == "multiply":
        return num1 * num2
    elif operation == "divide":
        return num1 / num2

with gr.Blocks() as demo:
    gr.Markdown("# Simple Calculator")
    num1 = gr.Number(label="First number")
    num2 = gr.Number(label="Second number")
    result = gr.Textbox(label="Result")
    with gr.Row():
        add_btn = gr.Button("Add")
        sub_btn = gr.Button("Subtract")
        mul_btn = gr.Button("Multiply")
        div_btn = gr.Button("Divide")
    add_btn.click(lambda a, b: calculator(a, b, "add"), [num1, num2], result)
    sub_btn.click(lambda a, b: calculator(a, b, "subtract"), [num1, num2], result)
    mul_btn.click(lambda a, b: calculator(a, b, "multiply"), [num1, num2], result)
    div_btn.click(lambda a, b: calculator(a, b, "divide"), [num1, num2], result)

demo.launch()

# Calling the deployed calculator's auto-generated API from another Python script
from gradio_client import Client
client = Client("https://1ab5014fd0d55f1a55.gradio.live/")
result = client.predict(13, 21, "add", api_name="/calculator")
print(result)  # 34

# CNN snake classifier deployment app (reconstructed per the chapter's description)
import gradio as gr
from fastai.vision.all import load_learner, PILImage

learner = load_learner("snake_model.pkl")

def predict(image):
    img = PILImage.create(image)
    pred, pred_idx, probs = learner.predict(img)
    return f"{pred} ({probs[pred_idx]:.4f} confidence)"

cnn_snake_app = gr.Interface(
    fn=predict,
    inputs=gr.Image(type="filepath"),
    outputs=gr.Textbox(label="Prediction"),
    title="Snake Poisonous Classifier",
)
cnn_snake_app.launch()

# Generating requirements.txt from Python
requirements = """gradio==5.12.0
fastai>=2.7.18
"""
with open("requirements.txt", "w") as f:
    f.write(requirements)
print(open("requirements.txt").read())
```
- **What it demonstrates**: the Gradio pattern used across all three deployed apps in the chapter (calculator GUI with button-bound functions, API client call to a live Gradio app, and the CNN inference app loading a pre-trained learner for image upload/classification), plus generating a pinned `requirements.txt` programmatically.

## Reference Tables

| Role | Responsibility | Built with |
|---|---|---|
| Client | UI/UX, user interaction | HTML/CSS/JS (web), Swift (iOS), Kotlin/Java (Android), or auto-generated by Gradio |
| API | Request/response contract | REST (HTTP + JSON) or GraphQL |
| Server | Core logic, data, computation | Python, PHP, Java, C++, etc. |

| Hugging Face deployment file | Purpose |
|---|---|
| `requirements.txt` | pinned dependency versions |
| `app.py` | application logic + Gradio UI + `.launch()` |
| (auto-generated) container | Hugging Face builds this from the two files above |

| Deployment transport methods | Notes |
|---|---|
| FTP | manual drag-and-drop file transfer; simple but less preferred for version control |
| GitHub (Hugging Face's preferred method) | tracks changes, supports rollback, enables collaboration |
| SCP | secure file transfer between hosts |

## Worked Example
The chapter deploys three progressively complex apps using the same pattern: (1) **Calculator app** — wraps the Ch3 `calculator()` logic in a Gradio `Blocks` interface with number inputs, four operation buttons, and a result textbox; `.launch()` produces a live, shareable URL plus an auto-documented REST API (tested via `gradio_client.Client(...).predict(13, 21, "add", api_name="/calculator")` -> `34`). (2) **Quick sort app** — GPT-4o is given only the input/output spec (unsorted list in, sorted list out) and designs the entire GUI itself, binding to the Ch4 `quick_sort()` function; tested on both a 10-number list and a 40-word list, both sorting correctly in real time. (3) **CNN snake classification app** — loads the exported Fast.ai `learner` object (no training data needed at inference time) into a `predict()` function wrapped in a Gradio `Interface` with an image-upload input; tested on real snake photos not in the training set, correctly classifying a poisonous snake (91.4% confidence) and a safe snake (84.9% confidence), and demonstrated working live on an iPhone via the camera-upload option (100% confidence on a third photo). Deployment to Hugging Face Spaces follows for persistence: create a Space (Gradio SDK, free 2-vCPU/16GB tier) -> upload `requirements.txt` (pinned `gradio==5.12.0`, `fastai>=2.7.18`) and `app.py` -> Hugging Face auto-builds the container and serves the app at a permanent URL, visually and functionally identical to the Jupyter-tested version.

## Key Takeaways
1. Separate client (UI), server (logic), and API (contract) concerns even in a beginner project — it clarifies where code belongs and why.
2. Use Gradio to get both a web GUI and a REST API from a single Python function, with no HTML/CSS/JS required.
3. Prefer server-side logic for anything involving sensitive data, proprietary algorithms, or heavy computation; client-side logic is only appropriate for simple, non-sensitive tasks.
4. Treat Gradio's `.launch()` live URL (72-hour expiry) as a quick-share/testing tool, and Hugging Face Spaces as the path to persistent, scalable, production-style hosting.
5. Pin exact library versions in `requirements.txt` to guarantee reproducible deployments.
6. Deployment at inference time needs only the exported trained model (learner/inference engine) — not the training dataset or data loader.
7. Even with AI-generated deployment code, review/debug it yourself; GPT-4o's first draft is a starting point, not necessarily the final version.
